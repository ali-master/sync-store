## Open your console

Start the API and open `/dashboard/` on the same server, for example `http://localhost:3000/dashboard/`. The dashboard ships with the API build and the Docker image. Docker users need no local Bun installation: follow [Self hosted](/docs/guides/self-hosted).

### First-time setup

On a new installation, the dashboard opens a three-step setup. A stepper at the top of the card shows which step you are on.

1. **Meet your console.** Select **Set up Sync Store**.
2. **Create your administrator key.** Run `docker compose logs api`, copy the **Setup code**, and enter it with a name for your administrator. Select **Create administrator key**.
3. **Save and start.** The key is shown once, with a **Copy** button. Save it in your password manager, confirm you saved it, and select **Open my console**.

The setup code proves access to the server. It remains valid across restarts until setup completes. Setup cannot be repeated after the administrator has been created, including when that key is disabled.

![First-time setup with a three-step stepper](/screenshots/onboarding.png)

### Sign in

An installation that is already set up shows the sign-in screen. Paste the administrator key and select **Open console**. When [single sign-on](/docs/guides/dashboard-sso) is configured, a **Continue with …** button above the key field signs you in with your identity provider instead.

![Sign-in with single sign-on and the administrator key](/screenshots/sign-in.jpg)

The credential stays in this tab's memory only: refreshing or closing the page signs you out. It is never placed in the URL or in browser storage. If the connection drops after key creation, use the [recovery command](#recover-administrator-access); do not reset your database.

## Find your way around

![Overview with live counts, records by collection and backend health](/screenshots/dashboard.png)

The sidebar groups the pages:

| Group        | Pages                                                                    |
| ------------ | ------------------------------------------------------------------------ |
| Start        | Connect your app, Overview                                               |
| Data         | Data explorer, Branches & commits, Version history                       |
| Access       | API keys, Projects, Tenants (platform administrator only)                |
| Monitor      | Sync health, Usage & quotas, Changes & growth, Connections, Activity log |
| Advanced     | Conflicts, User quotas, Analytics records, Archives                      |
| Installation | Settings (platform administrator only), System, About                    |

- **Sidebar.** The panel toggle in the top bar folds the sidebar to an icon rail. On small screens the sidebar is a slide-over menu that closes when you pick a page.
- **Breadcrumb.** The top bar shows where you are: installation or tenant, project, then page. It also shows the branch when a data scope is selected.
- **Connection status.** A badge reports **API connected**, **Connecting** or **Needs attention**. The refresh button reloads every view.
- **Command palette.** Press <kbd>⌘K</kbd> on macOS or <kbd>Ctrl</kbd>+<kbd>K</kbd> elsewhere, or select **Search**. Type to jump to any page, or to refresh data, open the API reference or sign out.
- **Appearance.** The appearance button cycles through **Light**, **Dark** and the device setting. **System** follows your device, including changes while the console is open. Your choice is saved in this browser; it never stores your key.
- **Addresses.** Each page has its own address, such as `/dashboard/storage` or `/dashboard/keys`. Search, page number and data scope are kept in the URL, so Back and Forward restore your view. Opening a saved link after refreshing still requires signing in.

## Overview

**Overview** shows what is in your database right now:

- **Stat cards.** Stored items and users, live connections, API keys and stored bytes.
- **Records by collection.** A donut chart with each collection's exact share and count. Select a segment to open that collection.
- **Backend.** MongoDB response time, runtime, database name, process uptime and lifetime key requests.
- **Access and connections.** A bar chart of keys, projects, tenants, sessions and quotas.

These are measurements taken when the page loads, not a history. For trends, use the [reports](/docs/guides/operational-reports).

## Records and the inspector

Most pages list one kind of record, 25 per page, newest first. Search matches identifying fields such as IDs, names, user IDs and keys, not every nested JSON value. The table never sorts or filters only the loaded page; search and paging happen on the server.

![Data explorer table with search and pagination](/screenshots/dashboard-data.png)

Select the arrow at the end of a row to open the **inspector**, a panel on the right. It shows the record and the actions that apply to it:

| Page            | What you can do in the inspector                                                                                                                                   |
| --------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Data explorer   | Edit a user's JSON value or delete the item. Saving shows a before-and-after review first. Writes use the same path as the SDK, so connected clients are notified. |
| Version history | Preview a retained version next to the current value and restore it. A restore is refused if the item changed since the preview.                                   |
| API keys        | Change permissions, project, key prefixes, quotas, expiration and network restrictions; disable or rotate the key.                                                 |
| Tenants         | Suspend or resume a tenant.                                                                                                                                        |
| Connections     | Disconnect a live Socket.IO session on whichever replica holds it. The client may reconnect unless its key is also disabled.                                       |
| Conflicts       | Record a resolution proposal with last write wins, first write wins or merge. Apply the resulting value yourself in Data explorer.                                 |
| User quotas     | Edit the stored quota settings as JSON. Not every stored limit is enforced.                                                                                        |

![Inspector panel editing a stored JSON value](/screenshots/dashboard-inspector.jpg)

Every destructive action asks for confirmation in a dialog. While a change is being saved, the inspector cannot be closed, so a save is never abandoned halfway. A stored value that is not valid JSON is shown as it is stored, rather than hiding the inspector.

### Create an application key

Open **API keys → Create API key**, give it a recognizable name, choose read and write permissions, and save. The secret is shown once in a highlighted block with a **Copy** button; copy it before closing the panel. Existing secrets are never shown again in lists or details.

Use a separate key for each trusted application, and never give the installation administrator key to an application or a playground user.

The key form also sets:

- **Project and key prefixes.** The project the key belongs to and the key prefixes it may read and write. A key's project cannot change after creation.
- **Expiration.** A date and time in your local time zone, chosen with your browser's date and time field. Leave it empty for a key that does not expire.
- **Quotas.** Requests per minute, hour, UTC day and UTC month.
- **Restrictions.** Allowed HTTP methods, IP ranges, website origins and user agents, and whether HTTPS is required.

Disabling a key blocks its next request. Rotation replaces the secret immediately: update your application's configuration, and disconnect old sessions when revoking access.

## Reports

**Sync health**, **Usage & quotas** and **Changes & growth** chart measured time series. Choose a window of one hour, 24 hours, 7 days or 30 days. Each headline number is compared with the preceding window of the same length.

A time bucket without a sample is drawn as a gap in the line, never as zero, and each chart states how many intervals have samples. Select a point to see every value recorded for that interval, or save the filters as a named view and export the table as CSV. See [Operational reports](/docs/guides/operational-reports) for what each metric means.

![Sync health report in dark mode](/screenshots/console-dark.jpg)

## Data scope

Pages that show one user's data have a **Data scope** bar. Use it to choose a tenant, project, user and branch. The scope is kept in the URL as you move between Data explorer, Version history, Connections, Conflicts and Branches & commits.

Tenant administrators stay limited to their own tenant; the server validates every scope change. **Reset** returns to all permitted data. Data explorer hides deleted items; their retained versions remain in Version history.

![Branches and commits for a scoped user](/screenshots/console-branches.jpg)

## Connect your application

**Connect your app** walks from a first credential to a verified change on a second client.

### Code examples

The JavaScript and React tabs show highlighted, ready-to-copy code. The `serverUrl` in the examples is the **Public API URL** from [Settings](/docs/guides/settings). Set it to the address your applications use, and the examples follow; until it is set, they show this page's own origin.

### Connection check

The optional connection check uses a **test application key**:

1. It obtains a short-lived user session.
2. It opens two independent SDK clients.
3. It writes one uniquely named value.
4. It waits for the second client to receive the change.

A connected socket alone never marks delivery complete; the check passes only when the second client receives the change.

The key must allow reads, writes, POST and DELETE, and access to `__sync_check__/`. Use a dedicated test user and an existing branch. The temporary value is removed after the check; its history, audit records and quota use remain. Credentials are cleared after the check and never included in the examples.

![Highlighted SDK example with the connection checklist](/screenshots/connect-app.jpg)

Your production backend must authenticate the user before issuing their session. See [browser sessions](/docs/guides/client-sdk#connect-a-browser-without-exposing-your-application-key). The check is an operator tool, not an application login flow.

## Settings, System and About

- **Settings** (platform administrator only) changes the public API URL, allowed browser origins, history retention, single sign-on and the metrics token. Values are saved in your database and apply without a restart. See [Installation settings](/docs/guides/settings).
- **System** shows the database, runtime, API origin, database latency and uptime, and the current operational boundaries.
- **About** shows the project's author with a link to their profile, the source repository, the documentation and the issue tracker, the version and the license. It also lists this installation's addresses: REST API, API reference, MCP server, Prometheus metrics and dashboard, each with a copy button.

About reads `apps/api/package.json` each time the page opens. Edit its `author`, `repository`, `homepage` or `bugs` fields, and the page follows without a rebuild or restart.

## Recover administrator access

From the server's repository directory:

```sh
docker compose exec api bun run admin:key
```

For a source installation, use `bun run --cwd apps/api admin:key` with the same database settings. This local command reads the existing credential; it does not reset the database or create another key. Protect terminal output and logs.

If the key has been exposed, rotate it in **API keys**. The current tab adopts the new secret; other sessions must sign in again, and every [single sign-on](/docs/guides/dashboard-sso) session ends.

## Deployment boundaries

The console grants installation-wide access. Keep it behind HTTPS and a trusted network or an authenticated reverse proxy. It is an operator console, not an end-user account system; application keys do not authenticate user IDs. With the shared Redis adapter, listing and disconnecting sessions works across API replicas. See [security](/docs/guides/api-key-management) and [deployment](/docs/guides/deployment).

## Customer workspaces and version graphs

Platform administrators create and suspend customer workspaces under **Tenants**. Each workspace has its own administrator key. **Branches & commits** provides user-scoped checkpoints, forks and whole-tree restores. See [Multi-tenancy](/docs/guides/multi-tenancy) and [Branches and commits](/docs/guides/branches-and-commits).

## Development

The console is built with:

- Tailwind CSS 4 and [beUI](https://beui.dev) components, charts and blocks;
- TanStack Router, which owns page and search URLs;
- TanStack Query, which owns server reads, cancellation and mutation invalidation.

Signing out cancels reads and clears the in-memory query cache. Mutations are not retried automatically.

Where things live, under `apps/dashboard/src`:

- **Pages:** each view is a file under `pages`, framed by `components/console-shell.tsx`.
- **Inspector:** one file per record type, under `components/inspector`.
- **beUI sources:** vendored in `components/motion`, `components/charts` and `components/agents`, so you can change them. Add another with `bunx --bun shadcn add @beui/<name>`; the registry is configured in `components.json`.
- **Theme:** colours, radius and fonts are tokens in `styles.css`, for light and dark.

The API build includes the dashboard automatically. For UI development:

- `bun run --cwd apps/dashboard dev` serves it at `http://localhost:4100/dashboard/`, and Vite proxies `/api` to `http://localhost:3000`. Set `API_PROXY_TARGET` to use another API.
- `bun --bun vite --config vite.mock.config.ts --port 4100`, from `apps/dashboard`, serves it against built-in sample data instead, with no API or database.
- `bun run --cwd apps/dashboard test` runs the unit tests, and `bun run --cwd apps/dashboard test:types` type-checks.
